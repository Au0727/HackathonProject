1. WHAT THE PROJECT IS
--------------------------------------------------------------------------------
The brief: design a delegated shopping agent that enforces a spending mandate.
Chosen scope: a household budget-holder ("Mei") delegates recurring household
purchases to an agent she does not trust with unlimited reach.

The system is TWO cooperating components:

  natural language -> [ SHOPPING AGENT ] -> up to 3 ranked candidates
                                                |
                                                v
                     [ FINANCIAL FIREWALL ]  (no LLM in this path)
                                                |
                                                v
                                        recommended purchase JSON

  Agent (BackEnd-AI)              Firewall (BackEnd-Supervisor)
  ---------------------------------------------------------------
  Question: what is worth buying?  Is this purchase authorized?
  Method:   LLM parse, search,     Deterministic rules only.
            ranking.               No model in the path.
  Output:   up to 3 ranked options APPROVE / ASK / DENY per plan
  Authority: the user's mandate    the user's authorization limits

Neither duplicates the other. The agent never decides whether money may move.
The firewall never looks at the product catalogue.

The final user-facing deliverable is: natural language in, a JSON document with
the recommended purchases out, printed on stdout.

5. ARCHITECTURE IN DETAIL
--------------------------------------------------------------------------------
5.1 THE SIX STAGES (one request)
  [1] INTENT EXTRACTION   LLM + JSON schema -> StructuredIntent
                          (product_keywords, max_base_price, max_total_cap,
                           preferred_brands, parse_notes)
  [2] SEARCH              keyword match with IDF weighting + token boundaries,
                          then cost math: total = price + shipping_fee
  [3] COMPLIANCE GATE     R-FIN-01 budget cap, R-SEC-01 trust audit
  [4] RANKING             deterministic selection -> up to --options candidates
  [5] AUTHORIZATION       firewall rules per plan -> APPROVE | ASK | DENY
  [6] REDUCTION           keep the best --keep approved -> final JSON

5.2 KEY DESIGN DECISIONS (and why - do not "simplify" these away)
  * MONEY IS Decimal, NEVER float. Coerced as Decimal(str(x)) at the model
    boundary. An agent one cent wrong on a cap is an agent that overspends.
    Decimal(3892.2) imports binary error; Decimal("3892.2") does not.
    Money is SERIALISED AS A STRING ("389.92") for the same reason.
  * THE FINANCIAL STOP IS DETERMINISTIC. An LLM may ADD a security finding; it
    can never CLEAR a budget breach. The LLM auditor is advisory only.
  * CAP SEMANTICS: "under $X total" (also all-in/delivered/including shipping)
    -> max_total_cap on price+shipping. Any other wording -> max_base_price.
    effective_cap() returns whichever was actually expressed.
  * IDF WEIGHTING: rarity = 1 + (total / (1 + hits)); field weights
    name:5 brand:4 description:1; expansion synonyms x0.6. Without it, a brand
    bonus floats an accessory above the requested product type (real bug fixed).
  * TOKEN-BOUNDARY MATCHING: keyword "mouse" must NOT match "Mousepad".
  * BRAND IS A TIEBREAKER, never part of the relevance score.
  * BUNDLE PROMOTIONS ARE LOGGED, NEVER APPLIED. They are conditional; applying
    one would compare a hypothetical against a real price.
  * TAX IS NOT MODELLED. total_cost = price + shipping_fee.
  * PRODUCT TEXT IS DATA, NEVER INSTRUCTION. Nine injection families detected by
    normalised pattern (zero-width characters stripped).
  * PRICE ANOMALIES ARE CONSERVATIVE: a false positive blocks a purchase the
    user legitimately wanted. Thresholds: shipping > 3x price; premium
    descriptor AND price < 15% of median (suppressed for component listings).
  * A MISSING MERCHANT MAPPING IS A DENIAL, not a guess
    (MERCHANT_RISK_DATA_UNAVAILABLE).

5.3 THE BRIDGE'S TWO EVALUATION PATHS (deliberate, documented in README 7.3)
    The firewall's priority engine (evaluate_plans) walks plans in rank order
    and STOPS AT THE FIRST APPROVE - ranks 2 and 3 are never evaluated. That is
    the right answer to "should this purchase go ahead?" but yields ONE plan.
    We want TWO authorized choices, so the bridge ALSO calls the per-plan rule
    pipeline (evaluate_plan) for every candidate and keeps the approved ones.
    Same rule set, different selection policy. Both are reported:
      best_options          = the authorized choices we return
      results[].firewall    = the priority engine's own single decision
    If strict "first APPROVE wins" is needed, read results[].firewall instead.

5.4 MERCHANT RISK IS NEVER READ FROM THE REPORT (firewall rule)
    The bridge maintains a trusted directory. It STARTS FROM the supervisor's
    merchant_catalog.json, PRESERVES every existing record, and assigns each
    unmapped product to one merchant per brand ("brand-kensington", ...).
    Scores are DETERMINISTIC (derived from ids) because the firewall promises
    identical decisions for identical inputs; a randomised score would break it.
    THE RISK BANDS ARE ILLUSTRATIVE VALUES WE AUTHORED - not observed data.
    Say so if asked. Never present them as evidence.

7. DETERMINISM - EXACT TRUTH
--------------------------------------------------------------------------------
Claim precisely this, no more:
  * With --offline, the recommended items and grand_total are identical on every
    run. results and grand_total compare equal across runs.
  * The DOCUMENT is not byte-identical: generated_at and the timestamped
    agent_report filename differ.
  * With a live API key, the intent stage may rephrase and the answer can vary.
    This was observed: the same request returned different products across runs.
Stages and their determinism:
  intent extraction  only offline (live LLM may rephrase)
  search + ranking   YES (fixed sort keys; product_id breaks all ties)
  compliance gate    YES (arithmetic + patterns, no model)
  firewall rules     YES (no language model in the path at all)
  merchant directory YES (scores derived from ids)
